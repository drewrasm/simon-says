### Elasticsearch v1 storage boundary

Track 2 owns the versioned mappings in `infra/elasticsearch`; Track 3 owns application queries. `segments-v1` is behind write alias `simon-says-segments`; `observations-v1` is behind write alias `simon-says-observations`. Each alias has exactly one backing index with `is_write_index: true`. Application writes use aliases with `require_alias: true`. Both mappings use `dynamic: strict` and omit shard/replica settings for Serverless compatibility.

- Finalized segment source fields match the `TranscriptSegment` schema in `packages/contracts`: `sessionId`, `epoch`, `windowId`, `segmentId`, `revision`, `startMs`, `endMs`, `timing: { kind, uncertaintyMs }`, `text`, `provenance`. Storage adds `expiresAt` as an absolute UTC date. ID: `sessionId:epoch:segmentId:revision`. Session, window, segment, and observation IDs use only `[A-Za-z0-9._-]`, so the `:` separator cannot be forged; epochs/revisions are positive integers. The setup tooling does not depend on the runtime contracts package.
- Only finalized revisions are indexed. Interim caption events remain unstored. Each subsequent final correction/repair has a new revision; keep earlier finals until lifecycle cleanup. `text` is a lexical `text` field with `copy_to: text_semantic`; `text_semantic` is `semantic_text`. Writers provide only `text`, avoiding duplicate application fields or inconsistent embeddings. Elasticsearch generates inference metadata internally. Time fields and uncertainty use `long`; fractional milliseconds in the runtime schema must be normalized to integer milliseconds at ingest before storage (Elasticsearch otherwise coerces them).
- Observation fields: `sessionId`, `epoch`, `observationId`, `frameId`, `checksum`, `objectKey`, `captureState`, `width`, `height`, `captureMs`, `glossaryTerms`, `expiresAt`. ID: `sessionId:epoch:observationId`, with the same identifier constraints. `glossaryTerms` is `keyword` with lexical subfield `glossaryTerms.text`. Repeated identical checksums at distinct capture times retain distinct observation IDs. Enum validation and required-field validation belong in runtime contracts/ingest; strict mappings reject unknown fields but do not enforce required fields or enums.
- Production revision writes use `op_type: create`; on 409, load and compare the existing canonical source. Identical source acknowledges the retry; changed source conflicts. Deterministic IDs alone prevent duplicate documents but do not prevent overwrites with the ordinary index API. Apply the same retry/conflict rule to observations. Never advance durable offsets/events on a failed write.

`ELASTICSEARCH_INFERENCE_ID` parameterizes the mapping; `.jina-embeddings-v5-text-small` is the [decided](decisions.md#confirmed-by-the-track-3-owner) default. Endpoint availability, cost, chunking and processing/data handling must still be confirmed in the cloud project before real content. Local verification uses `.multilingual-e5-small-elasticsearch`. `expiresAt` enables application filtering and durable cleanup jobs; it does not schedule Elasticsearch TTL deletion. Existing access, revision, expiry and redaction guards still apply. Time overlap is `startMs < requestedEndMs AND endMs > requestedStartMs`, filtered by session.

For v2, create new versioned mappings and indices, pause/fence writes, reindex finalized sources with unchanged IDs (regenerate embeddings if changing models), verify counts/ranges/relevance and catch up any queued writes. Atomically remove each old alias target and add its v2 target with `is_write_index: true`. Retain v1 for an approved rollback window, accounting for writes accepted on v2. Update setup's target version and the app key's exact backing-index names **before** cutover; rerunning the v1 setup after migration would restore v1 aliases. Migration/deletion requires separate approval; setup never mutates existing mappings.

Every source read (search, bookmark resolution, replay, or snapshot) checks current membership and access in Postgres before querying Elasticsearch, including after revocation. Enforce current source revision, expiry, and redaction guards before delivery. Never expose raw Elasticsearch responses or unauthorized counts.

Bookmark resolution queries Elasticsearch by fixed requested `startMs`/`endMs` on the session clock, filtered to segment revisions and frames. Include the valid frame at range start and changes inside it. Later arrivals can fill evidence but cannot move the requested range.

Transcript time ranges use our source clock mapped from sent audio offsets, not provider timestamps. Optional milestone 2–3 correction writes new revisions using the existing `corrected` provenance and preserves original text; it never blocks live captions.

Session states: setup, live, degraded, ended, expired. Keep transport health, transcript finality, bookmark persistence, and evidence completeness separate.

## Track 3 payloads

C0 schemas and inferred types are available through explicit package paths: [`session`](../packages/contracts/src/session.ts), [`bookmark`](../packages/contracts/src/bookmark.ts), [`search`](../packages/contracts/src/search.ts), and [`recap`](../packages/contracts/src/recap.ts). C1 implements session creation, invitation join, host claim, and membership checks. C2 implements owner-only bookmark saves, lists, deletion, and bounded evidence resolution. C3 implements session search. C4 implements owner-only recap generation, status reads, and Markdown export.

**Identity:** an anonymous signed-cookie principal per device, with no accounts. The server creates the principal row lazily on a mutating request. The `simon_says_principal` cookie contains a UUID and HMAC-SHA256 signature, uses HttpOnly, SameSite=Lax, a one-year lifetime, and Secure except over local HTTP. The server requires `SESSION_SECRET` with at least 32 characters at first use. The local placeholder in `.env.example` must be replaced for deployment; supply the same server-only secret to each app process. For local verification, export `DATABASE_URL` and `SESSION_SECRET` from `.env.example` before `pnpm --filter @simon-says/db migrate:deploy` and `pnpm dev`.

**Create and join:** `POST /api/sessions` accepts an optional title, trimmed and limited to 120 characters, and atomically creates the session and creator's host membership. Its 201 response contains `sessionId`, `hostPath` (`/host/<sessionId>#token=<token>`), `inviteCode`, and `joinPath` (`/join/<inviteCode>`). Only the SHA-256 host-token hash is stored; the raw token appears only in the creation response. The token travels in the URL fragment so browsers never send it in page requests, server logs, or referrers; the host page reads it and posts it to the host-claim endpoint. Invitations are 16–64 URL-safe characters and grant attendee membership through `POST /api/join`, never host credentials. A new or repeated attendee join returns 200 with `sessionId`, `membershipId`, and `role: attendee`. An existing host gets 409 with `{ error: "already_host" }` and keeps the host role. Unknown invitations, ended or expired sessions, and revoked memberships return 404 with `{ error: "not_found" }`. Server-issued membership, principal, and recap IDs are UUIDs. Bookmark IDs are client-generated UUIDs used as `:id` in `PUT /api/bookmarks/:id`, so creation needs no prior server round trip.

**Host claim:** `POST /api/sessions/:id/host` accepts `{ token }` and returns 200 with `sessionId`, `membershipId`, and `role: host`. A valid reusable host link grants host membership to another device; existing hosts keep access and the session's creator ID stays unchanged. Wrong tokens, non-UUID or unknown session IDs, ended or expired sessions, and revoked memberships return the same 404. Missing tokens and other invalid JSON payloads return 400 with `{ error: "invalid_request" }`. Bodies over 16 KiB, by declared `Content-Length` or by bytes read, return 413 with `{ error: "payload_too_large" }` before parsing. All three endpoints accept `application/json` and return `Cache-Control: no-store`, including errors.

**Access handoff:** import `readPrincipal` from `apps/web/src/server/access/principal.ts` and `requireMembership` with `RequireMembershipOptions` from `apps/web/src/server/access/membership.ts`. `readPrincipal()` returns `{ id }` or null without creating a row or cookie. `requireMembership({ sessionId, principalId: principal?.id, role? })` returns the current database membership with its session, excluding the host-token hash, or throws `AccessError` from `access/errors.ts`. Missing, revoked, expired, malformed-ID, and wrong-role access all throw status 404 and code `not_found`, without revealing session existence. Ended-session membership remains valid for permitted reads. Membership role is the authorization source; `hostPrincipalId` records the creator. Keep these database results server-side and set `Cache-Control: no-store` on downstream member responses.

**Pages (Track 1):** `/host/new` posts `POST /api/sessions` and navigates to `hostPath` with a full page load so the `#token` fragment reaches the browser. `/host/:id` renders the invitation QR code and join link only for a host membership on this device. Otherwise it reads `#token` once, posts it to the host-claim endpoint, and reloads; without a token it shows a not-the-host message. Both views remove the fragment from the address bar with `history.replaceState` so the token is not projected or copied. The QR code encodes the browser's origin plus `joinPath`. `/join/:inviteCode` shows the attendee disclosure and joins only on an explicit button press, so link previews and prefetchers never create memberships; it sends no referrer. `/join` holds the typed-code form, disabled until a short join code exists in this contract. `/session/:id` is the member-only caption reader; non-members, revoked members, and unknown or expired sessions all see the same not-joined page. Host and session pages render dynamically and are never cached.

**Notes UI (Track 1):** attendees write free-form private notes through `PUT /api/bookmarks/:id` as `live` bookmarks with a `note`, and read them through `GET /api/me/bookmarks`. The UI shows them newest first. **Approximate clock:** until Track 2's capture clock exists, the UI sets `markedAtMs` to time since session creation. It computes this from the server's elapsed time at page render plus monotonic time, so device clock skew does not move a mark. This must be replaced before notes resolve against captions. A draft keeps its bookmark and operation IDs for an identical resend. Text edited after a failed attempt is sent under new IDs with the same mark, and a 409 renews them, so an edit is never reported as saved when the server kept older text. Clearing a draft's text un-pins it. On wide screens (`lg` and up), `/session/:id` shows notes in a collapsible side panel with an inline form that pins on the first keystroke. Narrower screens get a bottom note sheet that pins when it opens. That sheet traps focus but has no backdrop or blur, so the transcript stays readable, and the separate `/session/:id/notes` page lists the notes.

**Bookmarks (C2):** `PUT /api/bookmarks/:id` accepts `putBookmarkRequestSchema`; the client generates the UUID ID. Non-UUID IDs return 404. Current membership in the body's `sessionId` is checked before reading evidence or saving, including for retries. Missing or revoked access and a bookmark belonging to another owner or session return the same 404, without its revision. The host has no ownership bypass. `expectedRevision: null` creates at revision 1 (201); the same ID and last applied `operationId` returns the existing bookmark (200). A different create operation on an existing owner ID conflicts. Positive expected revisions use one conditional database update, increment revision, and replace the stored operation ID; stale edits return 409 using `revisionConflictErrorSchema`. A missing update target returns 404. Operation IDs are unique per owner across bookmarks; reusing one for a different new ID returns 409 with null `currentRevision`. Only the last applied operation is retained, so a retry of an older mutation after a later edit conflicts.

`kind: live` stores `markedAtMs` and fixes the requested range to `[max(0, markedAtMs - 30000), markedAtMs]`. `kind: paragraph` stores the supplied segment ID, revision, and explicit range. Updates preserve the original anchor and requested range; later source arrivals only change evidence. Range editing is deferred. Times and uncertainty are non-negative milliseconds and may be fractional; equal endpoints are valid. Notes are limited to 4,000 characters; omitted notes preserve the existing note and responses use null for no note. `createdAt` and `updatedAt` are UTC ISO timestamps. `GET /api/me/bookmarks?sessionId=...` checks membership and returns only that owner's session bookmarks in `{ bookmarks }`, including anchors. `DELETE /api/bookmarks/:id` checks ownership and current membership for an existing record, returns 204, and returns 204 again when already absent. Missing signed identity and another owner's existing ID return 404. Every bookmark response, including errors, uses `Cache-Control: no-store`; PUT shares the access module's JSON parsing and 16 KiB body cap.

**Bookmark evidence (C2):** server-only `ELASTICSEARCH_URL` and `ELASTICSEARCH_API_KEY` configure read-only searches against `simon-says-segments` and `simon-says-observations`. No inference endpoint is called. After membership authorization, resolution reads all matching segment revisions and then rechecks all revisions of those segment IDs, selecting the highest revision per segment before testing overlap and expiry; a correction outside the range cannot resurrect older text. It takes the last observation at or before range start and observations after start through the inclusive range end, retaining unexpired frames. Track 2 has not fixed the `captureState` enum (its smoke writes `captured`), so every state except `stopped` counts as a frame; a stopped observation at range start prevents using an older frame. Missing or null source expiry remains valid until a deadline is supplied. `imageUrl` is always null today; private object keys are neither materialized nor returned.

Each resolution has a two-second total budget and at most four searches, each limited to 1,000 documents (the start observation search returns one). Timeouts, failed shards, invalid payloads, truncated results, unconfigured or unreachable Elasticsearch, and ranges with no indexed evidence yield `pending`; they never prevent durable bookmark saves. Nonempty partial evidence is `incomplete`. `complete` requires reachable Elasticsearch and contiguous latest-revision segment coverage of the requested range; frame presence does not determine text completeness. `actualRange` bounds the segment coverage clipped to the requested range, or is null with no segments; gaps remain visible through `incomplete`. Evidence preserves each full segment's source range and text. Clock uncertainty is the largest selected segment timing uncertainty, or zero without segments. Zero-width ranges cannot claim complete transcript coverage.

Save resolves synchronously. Reads retry at most five pending bookmarks concurrently, with no background jobs, choosing the least recently attempted first; each unresolved attempt touches `updatedAt` so later reads rotate through the rest. Zero-width ranges are never retried on read. Incomplete evidence is also retried on the next deliberate save. Lazy materialization updates evidence and `updatedAt` without incrementing the mutation revision or replacing its operation ID, and cannot recreate a deleted bookmark or overwrite a newer edit. An ES outage during an edit preserves already materialized evidence and actual range while marking completeness pending. Live ES resolution remains unverified. Private image delivery is deferred.

Postgres integration tests are separate from default `pnpm test` and require an explicitly configured database: after `pnpm services:up` and `pnpm --filter @simon-says/db migrate:deploy`, run `DATABASE_URL=<local-url> apps/web/src/server/bookmarks/test-integration.sh` from the repository root. The dedicated Vitest config rejects a missing `DATABASE_URL` and uses real Postgres with clearly labeled synthetic ES HTTP fixtures. It creates and removes only its own session and principal records.

**Search (C3):** `POST /api/sessions/:id/search` accepts `searchRequestSchema`. Query text is sent only in the POST body, never URLs, logs, or telemetry. Trimmed queries contain 1–500 characters, limits are 1–20 (default 10), and cursors are opaque. Non-UUID session IDs, missing signed identity, non-members, revoked memberships, and expired sessions return uniform 404 responses. The route reuses JSON parsing and the 16 KiB body cap. Current Postgres membership is checked before Elasticsearch and again before returning either results or an unavailable response. All responses, including errors, use `Cache-Control: no-store`.

One read-only `_msearch` HTTP request against `simon-says-segments` batches a relevance page (`bool.should` with keyword `match` on `text` and `semantic` on `text_semantic`), a keyword-only fallback page, and session-wide revision metadata. Only finalized revisions exist in this index; interim captions have no stored documents. Both relevance queries filter by session and exclude expired documents; null or absent expiry remains valid. Revision metadata deliberately includes expired and nonmatching corrections, so neither can resurrect earlier text. The server selects the highest revision per segment ID before returning its passage ID, segment ID/revision, full source range, and authorized excerpt. No private notes, principal IDs, raw ES responses, or counts enter search results.

Each relevance page reads at most `limit + 1` hits, sorted by descending score, segment ID, descending epoch, and descending revision. The next cursor encodes the last scanned hit's `search_after` tuple and retrieval mode, never the query. Cursors are opaque JSON strings and must travel unchanged in the POST body. Discarded stale hits can produce a short or empty page with a non-null cursor; continue until `nextCursor` is null. Cursors are for the same query and session; live indexing can change ordering between pages because this implementation does not hold an ES point-in-time snapshot. If the hybrid page fails in any way (missing or unauthorized inference endpoint, timeout, or shard failure), the already-batched keyword page supplies results; only the semantic clause differs between them. The response schema has no retrieval-mode field; keyword continuation stays keyword-only. Loss of semantic inference during hybrid continuation yields `unavailable`; restart without the cursor to allow keyword fallback.

The total HTTP budget is three seconds, with a one-second ES search timeout per subquery. Revision metadata collapses by segment ID with descending revision order, including expired corrections. The check accepts at most 1,000 distinct segments per session and requests one extra to detect truncation. A truncated revision check, failed shards, timeout, invalid response, or unreachable/misconfigured ES returns HTTP 200 with `{ results: [], nextCursor: null, indexingState: "unavailable" }`, never an authoritative empty result. Clients must treat `unavailable` as a failure. Successful searches report `current` for the revisions visible to that request; finalized-offset lag is not detected and `catching_up` is not emitted.

To save a selected result, use the existing `PUT /api/bookmarks/:id` with a `paragraph` anchor containing its `segmentId`, `segmentRevision`, and `range`. Creating a paragraph bookmark now checks the latest stored revision, expiry, session, segment identity, and range containment immediately before saving, then rechecks Postgres membership. Missing, superseded, expired, or out-of-range sources return 404; unavailable source validation returns 503 with `{ error: "source_unavailable" }` and creates no bookmark, so the client can retry. Live saves retain C2's durable pending behavior. Existing bookmark edits preserve their original anchor, and an already-applied operation remains an idempotent retry.

Search integration tests are separate from default `pnpm test`: after starting and migrating local Postgres, run `DATABASE_URL=<local-url> apps/web/src/server/search/test-integration.sh`. They use real membership records and labeled synthetic ES HTTP responses, including revocation during a source request and selecting a search result through the existing paragraph bookmark mutation. They do not prove live Elasticsearch semantic retrieval. Compose does not include Elasticsearch; a separate local start-local installation or authorized cloud verification is needed for that gate.

**Recaps (C4):** `POST /api/sessions/:id/recaps` accepts `createRecapRequestSchema`: a retry-stable UUID `operationId` and 1–50 `{ bookmarkId, expectedRevision }` selections (`maxRecapBookmarks`). Duplicate bookmark IDs return 400; an empty list is invalid and makes no model call. Session IDs must be UUIDs. Current membership is required before processing the body or looking up selections. Missing identity, invalid or inaccessible sessions, and bookmarks outside the caller's owner/session scope return uniform 404 without exposing revisions. Only an owned bookmark at a different revision returns 409 using `revisionConflictErrorSchema`. The host has no ownership bypass. Bodies use the existing JSON parser and 16 KiB cap.

Creation persists the owner, session, operation ID, bookmark ID/revision snapshot, `pending` status, and timestamps before returning 201 with `{ id }`. Concurrent retries converge on one row. Reusing the same operation ID in the same session returns that recap (200), including after selection edits or a failed generation, without scheduling another call. Reusing it in another session returns 404. A deliberate regeneration needs a new operation ID. Session deletion cascades to its recaps.

Generation is bounded. Each owner may have one active (`pending` or `running`, updated within the last 90 seconds) recap per session; a new operation ID while one is active returns 429 `{ error: "recap_in_progress" }`, checked after selection validation under a per-owner/session advisory lock so concurrent creates cannot both start. A concurrent retry of the winning operation ID still returns that recap. The process also runs at most four background generations at once; further creates return 429 `{ error: "recaps_busy" }` before any row is written, including retries of existing operation IDs, so clients retry later. This in-process counter matches today's single replica. The prompt includes whole passages in selection order up to 60,000 serialized JSON characters; later passages are omitted, never truncated, so excerpts stay verbatim.

The request registers Next.js `after()` (verified in installed Next 16.4.5) to claim `pending` → `running` once. It loads only selected materialized evidence and sends only bookmark IDs, segment IDs/revisions, and passage text to OpenAI through pinned `ai` 7.0.165 / `@ai-sdk/openai` 4.0.111 structured output. Notes, other bookmarks, frame URLs, and other session content never enter the prompt. Passages are untrusted source data. Server-only `RECAP_MODEL` defaults to `gpt-5.4-mini`, present in the installed OpenAI provider's model catalog; the model's live behavior remains unverified without a key. `OPENAI_API_KEY` comes from the server environment (cluster Secret `app-credentials`), never a public variable or client prop. Provider response storage is disabled with `store: false`; SDK input/output telemetry is disabled. No prompt, passage, note, model output, or provider error body is logged.

No nonempty materialized segment text means `failed` with `failureReason: no_resolved_evidence`, without calling the model. Each takeaway must retain at least one valid citation to a selected bookmark's exact segment revision. The server drops unknown citations, blank or nonverbatim excerpts, and takeaways left without citations. Excerpts are copied from stored evidence after substring verification; source ranges and nullable frame IDs come only from that bookmark's stored evidence. All-invalid output fails with `no_valid_citations`. The model has no tools or source lookup. A final membership check and transactional bookmark revision recheck precede saving; changed or deleted selections yield `stale` and no takeaways. Model/network/structured-output failure yields `generation_failed`; a 45-second model budget aborts and yields `generation_timeout`. There are no automatic provider retries. Failure never changes or deletes bookmarks.

`GET /api/me/recaps/:id` validates owner and current membership, including for ended sessions, and returns `recapResponseSchema`: `id`, `status` (`pending|running|ready|failed|stale`), `takeaways`, and nullable `failureReason`. Every read rechecks selected bookmark revisions; edits and deletion invalidate results as `stale` and clear their takeaways. Pending/running rows unchanged for 90 seconds become `failed / background_interrupted` when polled, covering process termination and lost background callbacks. This is request-scoped execution for today's single replica, **not** a durable queue or restart retry guarantee. Source-redaction/expiry endpoints and durable cleanup remain deferred; current membership and session expiry checks still apply.

`GET /api/me/recaps/:id/export` uses the same ownership, membership, and staleness checks. Ready recaps download a `text/markdown` attachment with escaped takeaway text, cited passages, segment revisions, source ranges, and optional frame references. Other statuses return 409 `{ error: "recap_not_ready" }`; inaccessible IDs return 404. All recap responses and errors use `Cache-Control: no-store`. HTML export and image embedding remain deferred.

Recap Postgres tests remain outside default `pnpm test`: after local services and migrations, run `DATABASE_URL=<local-url> apps/web/src/server/recaps/test-integration.sh`. They use real Postgres and explicitly synthetic stored evidence and mocked generation; each run cleans only its own records. The rerunnable production-HTTP check is `DATABASE_URL=<local-url> node --conditions=react-server --import tsx apps/web/src/server/recaps/verify-local.ts http://127.0.0.1:<port>`. It inserts synthetic evidence directly because Elasticsearch is unavailable and checks the real provider only when `OPENAI_API_KEY` is present. No OpenTelemetry/Dash0 app instrumentation exists on this slice's base, so no tracing stack is added here.

## Event and mutation rules

Each session event carries a cursor, session ID, event kind, entity ID/revision, and source time where applicable. Event kinds include transcript update, frame observation, capture state, and clock heartbeat. Use a discriminated schema per kind.

Private bookmark and recap status never enters the shared caption channel. Use bounded polling of owner-only bookmark and recap reads while the relevant view is open, including stale-result changes. Validate membership on stream creation and enforce revocation while connected. Bound payload sizes, queue sizes, and session duration. Pod restart or rollout reconnects transport without ending the session. Persist leases and replay state outside pod memory; reject stale epochs across all pods. Provider reconnects retain source-clock mapping. Persist a finalized transcript offset and separate audio acknowledgments in Postgres; replay retained, unfinalized audio with overlap deduplication. Report unrecoverable transcript gaps separately from audio gaps. Disable shared caching for member and owner responses.

Duplicate audio epoch/sequence with the same checksum acknowledges the existing chunk; changed content conflicts. Bookmark retries reuse their bookmark ID and operation ID; a deliberate second mark gets new ones. Stale edits conflict instead of overwriting. Save acknowledgments distinguish local pending data from server persistence.

For today’s C4 cut, recap requests persist an owner-scoped status row and register request-scoped background generation, then return the recap ID; the durable job, retry worker, and restart recovery are deferred. Operation IDs reuse the same recap without another model call. Generation binds to selected bookmark revisions and validates selected source IDs and verbatim excerpts. Recheck revisions before saving and on owner reads; edits/deletion mark stale and remove takeaways. Redaction/expiry invalidation beyond current access checks remains part of the deferred lifecycle work. Empty or unresolved evidence never produces unsupported takeaways. See the C4 payload rules above for timeout and interruption behavior.

## Live caption ingest and events

Implemented as schemas in `packages/contracts` and pure rules in `packages/domain`; the server pipeline and host capture module that use them are separate changes. Runtime behavior with a live provider is unverified.

**Audio frames.** The host sends binary WebSocket messages: a 16-byte little-endian header (version 1, kind 1 = PCM16 mono, reserved, epoch u32, sequence u32, sample offset u32) followed by PCM16 samples at 24 kHz. Frames normally carry 2,400 samples (100 ms) and at most 4,800. The sample offset counts samples since capture start and is the session source clock: `ms = sampleOffset / 24`. A u32 offset covers about 49 hours. The host keeps up to 120 s of unacknowledged frames for resend.

**Control messages.** After connecting, the host sends `hello` with its epoch, highest unacknowledged sequence, and sample rate. The server replies `ready` with the sequence it has acknowledged through; the host resends everything after it. `ack` confirms receipt into the server ring buffer, not durable storage. Raw-audio persistence (the `AudioChunk` record) is deferred for the hackathon: until it exists, an acknowledged frame lost in a pod restart cannot be replayed, and the range becomes a visible `caption.gap` with reason `audio_missing`. Transcript finalization stays separate from receipt. `rejected` carries `unauthorized`, `stale_epoch`, `session_ended`, `invalid_frame`, `sequence_conflict`, or `overloaded`, and whether retrying can help.

**Segments.** The fields and identifier rules are defined in the Elasticsearch v1 storage boundary above. Provenance is `live`, `corrected`, or `repaired`. Live timing is always `estimated` with an `uncertaintyMs` half-width, because streaming text has no provider timestamps. A `caption.final` event only carries segments from its own session, epoch, and window.

**Shared caption events** (SSE, discriminated by `kind`, each with `cursor` and `sessionId`):

| Kind              | Meaning                                                                                                                      |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `caption.interim` | Live, unstored text for one window with its start and estimated end; each event replaces that window's previous interim text |
| `caption.final`   | Final timed segments for a window; supersedes its interim text                                                               |
| `caption.gap`     | A source range with no transcript, because transcription failed or audio is missing                                          |
| `capture.state`   | Session state, audio receipt (`receiving`, `stalled`, `stopped`), and caption lag                                            |
| `clock.heartbeat` | Latest source-clock time received from the host                                                                              |

**S3 development scope.** With `DATABASE_URL` configured, the caption authority verifies the signed principal cookie using Track 3's credential helper and calls `requireMembership`: `role: "host"` for ingest, any active membership for SSE. Ingest additionally requires session status `setup`, `live`, or `degraded`; an ended session receives `session_ended` with `retryable: false` on admission or the periodic re-check. An ended session remains readable by permitted SSE members. Database auth takes precedence over `CAPTIONS_DEV_SESSION`. Without database configuration, that dev flag enables only one session outside production; production continues to reject all access. Unauthorized ingest upgrades receive `{ type: "rejected", reason: "unauthorized", retryable: false }` and close code 1008; unauthorized HTTP reads return 404 without revealing session existence. Membership is checked before replay/snapshot and every 30 seconds on open connections. Revocation or a failed/timed-out access check closes ingest with `unauthorized` and destroys SSE, discarding queued events. Access checks have a five-second deadline; revocation detection can therefore take up to 35 seconds. Track 3 exposes no lease/epoch API, so epoch fencing remains per-session process memory; durable cross-pod fencing is still pending. Higher epochs fence old connections against further ingest and finish their accepted tail audio. Same-epoch reconnect within the grace period resumes the same window and receipt progress, but must resend only unacknowledged frames; skipped sequences or discontinuous sample offsets are rejected as `invalid_frame`. Sequences start at zero for a new epoch; the first sample offset may be nonzero. Duplicate retained sequences with changed samples/offsets conflict; duplicates older than the ring are rejected. Frames are retained for at most 120 seconds / 6,000 frames.

The development `ready` and `ack` positions represent **process-local receipt**, not the durable audio acknowledgments required above. They cannot survive process restart. This is a dev-only exception, not milestone 1 durability acceptance. Segment sink completion precedes `caption.final`; the configured Elasticsearch sink completes a create-only bulk write before publication; without ES configuration the development in-memory implementation is not Elasticsearch durability and reports `missing_elasticsearch_config`. Search visibility follows index refresh (`refresh: false`). Sink failure reports degraded state with `reason: segment_sink_failed` and a `transcription_failed` gap for that window, with no final. Provider failure gets two retries (three attempts total), then the same exact-range gap. `capture.state.reason` is an optional content-free enum: `missing_provider_key`, `missing_elasticsearch_config`, `transcription_failed`, `segment_sink_failed`, or `backlog_limit`; it never contains provider errors. Missing provider configuration emits `missing_provider_key` and declines audio without acknowledgment.

**End of input.** There is no explicit stop control message. A host WebSocket close with code 1000 ends input and calls `finish()`, committing the active provider stream and awaiting its final or exact-range gap. A periodic membership re-check that detects an ended session also ends input and finishes the accepted tail without reconnect grace. Other closes (including server-requested 1012 reconnect) retain the same window for `CAPTION_RECONNECT_GRACE_MS` (default 10,000 ms; integer 0–60,000). A successful same-epoch hello cancels that timer; expiry finishes the tail. Once input ends, same-epoch hello is rejected as `session_ended`; restart needs a higher epoch. Newer epochs finish the old manager independently while accepting the new host. Each finish has a five-second budget; unresolved provider or sink work is fenced and becomes a `transcription_failed` gap, with late finals suppressed. SIGTERM rejects new input, finishes accepted windows within five seconds, and keeps SSE open until finals/gaps are enqueued, inside the ten-second process drain budget.

The single-replica SSE log retains 500 events. Missing, invalid, future, or too-old `Last-Event-ID` produces a bounded recent snapshot: the latest capture state, up to 500 latest finals, and retained log events, deduplicated and sorted by their **original** cursors. A valid old cursor filters all entries at or before it, so a disconnect partway through a snapshot resumes the remaining retained finals without duplicates or skips. No snapshot cursor is minted or advances the log. Clients still upsert stable segment IDs after history expires; this is not complete history. Durable full-session replay remains pending. Each subscriber queues whole SSE frames, pauses after `write() === false`, and resumes on `drain`. Queued plus socket-buffered bytes are capped at 8 MiB; a replay/snapshot batch is preflighted before any of it is written, and cap overflow destroys only that subscriber without emitting a partial frame or any of the rejected batch. Heartbeats carry the latest received source time every 15 seconds. Product transports share a 32-connection cap and 30-minute connection lifetime; a hello is required within five seconds. Retained sessions are capped at 16. Provider attempts have a 45-second deadline; window backlog is capped at eight. A full backlog rejects further ingest as retryable `overloaded` rather than dropping accepted samples.

**Window rotation.** One window is one provider streaming call. Cuts aim for pauses so words stay whole, in tiers: the first pause of at least 300 ms after 15 s; a 150 ms pause (a breath) after 20 s; after 25 s, the first quiet unit or speech low point (quietest quarter of the last second and 3 dB under its median); and at 27 s regardless. Only the last two tiers can split a word; each cut records its tier so the rate can be measured. A quiet run never spans a gap in the audio. The next window is pre-opened 1 s before the minimum. Pauses are judged on 20 ms units against a noise floor equal to the 10th percentile of the last 5 s of levels, relearned after an audio gap. Every sample before a cut belongs to the earlier window.

**Timing estimate.** Interim text is placed at the audio offset sent when it arrived, minus measured lag. Final text is split into sentences; each sentence end maps to the delta arrival timeline by relative character position. Ranges are contiguous, inside the window, and the last sentence ends at the window end. Without deltas, sentences are spread linearly with uncertainty of half the window.

## Search and source durability

A search request carries query text, a bounded result limit, and an optional opaque cursor. Keep query text out of URLs and telemetry. Require current session membership before searching. Return passage IDs, segment IDs and revisions, source ranges, authorized excerpts, and an indexing state such as current, catching up, or unavailable. Do not treat stale or unavailable search as an authoritative empty result.

Keyword search plus `semantic_text` operates over shared segments and glossary terms in Elasticsearch. Confirm the inference endpoint and processing settings in the selected project before assuming Jina or another model. Return current segment revisions and source ranges, preserving earlier revisions for provenance.

Selecting a result creates an owner-scoped paragraph bookmark through the existing mutation contract. Validate current source access and revisions again at save time. Search scores never establish evidence or change source timestamps.

Elasticsearch source writes participate in durable acknowledgment. Do not advance the Postgres finalized-transcript offset or publish a durable source event before the corresponding content is durable. Milestone 1 must specify cross-store write ordering, retry/reconciliation, visibility, and crash recovery; audio receipt acknowledgment and transcript finalization remain separate. Elasticsearch failures visibly degrade captions and retain retryable source work or expose gaps, never silently lose content.

Use durable Postgres cleanup jobs and deletion tombstones/guards so delayed writes cannot restore redacted or expired documents. Verify interrupted Elasticsearch expiry, redaction, and deletion resume safely. Materialize permitted selected evidence before shared-source expiry. Revocation denies access immediately through Postgres checks even while cleanup is pending.

## Runtime and telemetry

Checkpoint 0A implements `/healthz` as process liveness and `/readyz` as Next.js prepared and not shutting down (200/503). Persistence is not required by the current shell. Elasticsearch is required persistence for milestone 1: expose its failure in readiness and caption health, and define degraded ingest/retry behavior when core routes need it. A Dash0 outage must not make live caption service unready. Neither endpoint exposes configuration or credentials. SIGTERM stops admission, ends SSE, closes WebSockets with 1012, and drains within 10 seconds (20-second pod grace).

0A transport probes are separate from product APIs: opt-in `PROBE_TOKEN` authentication, `/api/probe/ws` accepts only text `ping` and replies `pong`, and `/api/probe/sse` emits one constant heartbeat per second without compression/buffering. They share a 16-connection cap and 30-second lifetime; WS payloads are limited to 32 bytes and 30 messages. Missing configuration disables probe access; invalid credentials reject before streaming/upgrade. They do not establish product identity or durable replay. See [runtime details](deployment.md#local-foundation).

Use allowlisted telemetry fields for operation, outcome, duration, source lag, retry count, and opaque correlation IDs. Never export query text, transcript, frame content, notes, prompt bodies, tokens, or signed URLs. Verify both manual spans and automatic instrumentation.
