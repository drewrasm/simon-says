## Local foundation

`apps/web/server/index.ts` owns HTTP and upgrades. Next builds normally (no standalone output); esbuild bundles the Node entry point, workspace TypeScript exports, and their Zod dependency (leaving direct npm dependencies external), and `pnpm deploy --prod --legacy` packages its production dependency closure. The runtime image contains the build and production dependencies, runs as UID/GID 1000, and excludes environment files. Node 22.22.0 and pnpm 11.24.0 are pinned. Prisma generation is a build step. The image also carries the `@simon-says/db` production closure at `/app/migrate`: the Prisma CLI, its config, the schema, and committed migrations. Only the migration Job uses it; app pods never migrate. The access and bookmark routes import the database client; `apps/web/next.config.ts` bundles `@prisma/client` and `pg` because Turbopack otherwise emits hashed external symlinks under `.next/node_modules` that break once `.next` is copied into the runtime image. Those routes need `DATABASE_URL` and `SESSION_SECRET`, which the Deployment injects from Secrets `db-app` and `simon-says-session`.

Readiness means Next is prepared and shutdown has not started. Liveness means the HTTP process is alive, including during preparation. External providers and persistence are deliberately excluded until core routes require them. Optional Secret references do not verify provider configuration or connectivity. `PORT` and the opt-in probe credential are validated at startup without logging values. Provider validation belongs at each provider's future initialization boundary.

The content-free authenticated transport probes, bounds, commands, and shutdown behavior are documented in [README](../README.md#local-container-and-transport-probes). They prove transport only; device identity and session membership are implemented as described in [contracts](contracts.md#track-3-payloads); leases and replay are process-local, not durable. Caption connections re-check membership every 30 seconds. Unknown production upgrades are rejected before handshake. Development forwards Next's HMR upgrades after preparation.

`infra/k8s` renders the app, Service `app:80` → 8080, starter HTTPRoute, and a one-instance CloudNativePG database. `infra/argocd/application.yaml` points at this repository and `infra/k8s`, enables automated sync with pruning and self-healing, and is applied and active; see [team environment](#team-environment). The app preStop hook waits five seconds for endpoint removal to propagate before SIGTERM; this and the ten-second server drain fit inside the 20-second grace period. The five-second delay is an estimate; adjust it when gateway rollout testing measures propagation. Sync waves order each sync: the database `Cluster` (wave -2), then the `db-migrate` Job (an Argo CD `Sync` hook in wave -1), then the app (wave 0). See [database migrations](#database-migrations). The consolidated `check.yml` keeps the `check` and `container` jobs: installs, migrations and a connection check against a Postgres service container, checks, Next/server build, amd64 image build, the migration command inside the built image, local transport/shutdown probes, and offline rendering. PR jobs have read-only repository permissions; the gated main-only publish job has narrowly scoped write permissions.

## Database migrations

Job `db-migrate` runs `prisma migrate deploy`, then `pg-boss migrate` when the image ships the pg-boss CLI, from `/app/migrate` in the same image as the app, so a deploy PR's tag bump moves both. Prisma owns the app schema; pg-boss creates and upgrades its own `pgboss` schema, and app pods start pg-boss without migrating. The CLI check covers the first sync after the Job command changed, which can still run an image from before pg-boss; that image runs no jobs, and the deploy-tag sync installs the schema. `DATABASE_URL` and `PGBOSS_DATABASE_URL` both come from the CloudNativePG Secret `db-app`, key `uri`. Argo CD runs the Job on every full application sync, including automated syncs of a new `main` revision; both commands apply only pending migrations, so a sync without new migrations is a no-op. Self-heal and other selective resource syncs skip hooks, so they can restart app pods without migrating; after a failed migration, recover with a full sync through Radar. The `BeforeHookCreation` delete policy replaces the previous Job at the next sync and keeps the last run's logs until then.

A plain `PreSync` hook would run before the `Cluster` exists on the first sync and block it, so the Job is a `Sync` hook in wave -1 after the `Cluster` in wave -2. Argo CD waits for the `Cluster` to report healthy before wave -1 only if its health check for `postgresql.cnpg.io/Cluster` is available. Otherwise the pod waits for `db-app`, and the Job retries connection failures with exponential backoff (`backoffLimit: 6`) until `activeDeadlineSeconds: 600`. A failed Job fails the sync, so the app Deployment keeps its previous pods. The Job requests 100m CPU / 128Mi with limits of 500m / 512Mi, and runs only during syncs.

An image without `/app/migrate` cannot run the Job: the sync fails and the previous app pods keep serving until a deploy PR pins an image that contains the migration closure. With `AUTO_DEPLOY=false`, merge that deploy PR manually.

## Release flow (C1a)

The release flow is publish → guarded deploy PR merge → Argo CD sync. Without a `DEPLOY_TOKEN` whose actor has ruleset bypass, the `main` ruleset refuses deploy PR merges, and an admin with bypass merges them by hand; see [ruleset bypass](#ruleset-bypass-one-time-admin-setup-drew). Actions changes `main` only through PRs.

1. `check` and `container` must pass before the publish job builds Linux/amd64 and pushes `ghcr.io/drewrasm/simon-says:<full-commit-sha>` plus `:main` using `GITHUB_TOKEN`. Publication runs only on main pushes or manual dispatch on main. Workflow and publish concurrency keep the newest run, cancelling superseded work; freshness checks reject older source SHAs even if jobs arrive out of order.
2. After publication, `scripts/propose-deploy.sh` opens or reuses `deploy/<sha>`. Only the app `images[].newTag` in `infra/k8s/kustomization.yaml` changes. Before merging, the guard compares git trees from the PR merge base to its pinned head: exactly one regular file modification, exactly the app tag replacement to the published full SHA, with every other byte unchanged. Unexpected keys, files, modes, or tags leave the PR open with a `::warning::` and summary reason.
3. Actions merges immediately using `gh pr merge --merge --admin --match-head-commit <validated-head>`. It does not use `--auto`, require `allow_auto_merge`, dispatch checks on deploy branches, or wait for Gitar. Machine-generated, single-value deploy-tag PRs are the sole exception to Gitar review ([decision](decisions.md#c1a-release-tags)). Source PRs retain CI and Gitar review. `contents: write`, `packages: write`, and `pull-requests: write` are scoped to the publish job; other jobs retain read-only contents access. Deploy API calls use optional `DEPLOY_TOKEN`, falling back to `GITHUB_TOKEN`; GHCR publication and git branch pushes keep the job token. The deployment token needs repository Contents and Pull requests read/write permissions and its actor needs ruleset bypass. Actions PR creation must remain allowed by repository policy.
4. Freshness checks fetch full history when shallow and compare the published SHA with current main, excluding only the kustomization. Before proposing a current release, older open same-repository `deploy/<full-sha>` PRs are closed only when their SHA is an ancestor of the published SHA; unrelated and newer branches are preserved. Source changes close an existing stale deploy PR; the job summary gives the reason without posting a comment. Freshness is checked before publication, before proposing, and immediately before merging. An already-merged PR is a successful no-op on retry; a closed PR is left closed. Successful summaries say `Deployed <sha> via #<pr>`. This records the Git merge, not verified rollout health. The head-match option protects against PR edits; GitHub's merge API does not provide an atomic expected-base check, so a source merge in the final fetch-to-merge window may briefly deploy the previous image until the newer release succeeds.
5. Argo CD watches `main` and syncs the committed image, running the `db-migrate` Sync hook Job (same image tag) before the app rollout. Kustomization-only pushes to main are ignored, preventing release loops with either token. The `pull_request` trigger has no path exclusion so human-created deploy and rollback PRs run `check` and `container`. Check Radar after runtime merges and record rollout evidence on the Shortcut story.

### Ruleset bypass: one-time admin setup (Drew)

Ruleset **main** (id `26887534`) requires a PR plus `check`, `container`, and `Gitar`. The publish job already checked the source SHA before creating its machine-generated tag PR. Those checks do not automatically satisfy checks on the deploy PR's different head. Without bypass, the ruleset refuses the merge even after the tag guard passes. Gitar may not review bot PRs. GitHub's current [GITHUB_TOKEN documentation](https://docs.github.com/en/actions/concepts/security/github_token) says bot-created PR checks may require approval. Neither behavior provides unattended deployment.

GitHub [documents ruleset bypass for GitHub Apps and eligible roles](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository), and [`gh pr merge --admin`](https://cli.github.com/manual/gh_pr_merge) requests merging despite unmet requirements. The flag does not grant bypass permission. The built-in **GitHub Actions** integration's availability in the bypass picker and use by `GITHUB_TOKEN` have **not** been confirmed; do not rely on that proposed setup. Use this documented alternative:

1. Drew supplies a fine-grained PAT restricted to this repository, with Contents and Pull requests read/write, owned by an actor with an eligible bypass role (for example Repository admin). Alternatively, use a short-lived installation token from a dedicated installed GitHub App with the same permissions; token generation/rotation is operator-owned.
2. In the repository, click **Settings → Rules → Rulesets → main → Bypass list → Add bypass**. Select the token owner's eligible role (for a PAT), or the dedicated installed GitHub App, then **Add Selected → For pull requests only → Save changes**. Prefer PR-only bypass to retain the PR audit trail. Role bypass applies to every actor in that role; a dedicated App narrows the exception. If GitHub Actions is offered in this picker, its job-token bypass can instead be tested by Drew; support is not assumed here.
3. Click **Settings → Secrets and variables → Actions → Secrets → New repository secret**; name it `DEPLOY_TOKEN` and supply the deployment token. The workflow only reads this optional secret. PAT/App-authored PR events can trigger checks, but guarded deploy merges deliberately bypass required checks including Gitar rather than waiting for them. Source PRs still require normal checks and review.

Without a usable bypass, a refused merge emits an explicit `::error::` naming this setup, leaves the PR open, and fails the job (an already-merged PR remains a successful retry). Inspect the original CLI error too: conflicts, expired tokens, or other policies can also refuse merging.

For immediate recovery, an admin with ruleset bypass can inspect and manually merge the current open deploy PR, choosing **Merge without waiting for requirements to be met** if offered, or `gh pr merge <current-deploy-pr> --merge --admin` with that admin's authentication. Admin status alone is insufficient without ruleset bypass. Recheck source freshness and migration-image compatibility before manually merging an older release.

### Pause, recovery, and rollback

Set repository Actions variable `AUTO_DEPLOY=false` to leave published-image deploy PRs open for manual review and merging. Unset or any other value defaults to enabled. This pauses automatic tag merges, not image publication or Argo CD syncing existing Git changes. Cancel any already-running release before relying on the variable; Actions variables are captured for the run.

To resume, remove the variable or set it to `true`, then run `check.yml` with `workflow_dispatch` on `main` (Actions → check → Run workflow → Branch: main). This checks, publishes, and proposes the current SHA; rerunning a failed job reuses its existing PR. Closed stale PRs are not reopened.

To roll back, pause automatic deploys first, then open a reviewed PR reverting the deploy-tag commit (or the merge with the appropriate mainline), or open a deploy PR setting `newTag` to a previously published known-good SHA. Merge it to let Argo CD sync. Manually authored rollback PRs follow normal review. A rollback changes runtime only; it cannot undo database migrations. Keep automatic deploys paused until a forward fix is ready, otherwise the next source merge will select a new image.

Local guard verification: `python3 scripts/test-deploy-diff.py` creates real fixture commits in a scratch git repository; it accepts a tag-only diff and rejects another key, another file, a wrong SHA, and a mode change. Run `python3 scripts/test-propose-deploy.py` for mocked merge-refusal, stale-cleanup, and pause coverage. Run `actionlint`, `bash -n scripts/propose-deploy.sh`, and `shellcheck scripts/propose-deploy.sh` for CI/script validation. Check rollout health after each runtime merge.

### Data-bearing resource protection

Automated sync and `selfHeal: true` remain enabled. The CloudNativePG `Cluster` `db`, which provisions the database PVC, carries `argocd.argoproj.io/sync-options: Prune=false,Delete=false`. Argo CD [combines resource sync options with commas](https://argo-cd.readthedocs.io/en/stable/user-guide/sync-options/): `Prune=false` retains a resource removed or renamed in Git, and `Delete=false` retains it during Application deletion. Apply the same annotation to every future data-bearing or PVC-bearing resource in `infra/k8s`, including explicit PVCs and workloads that own persistent storage. The database Cluster is currently the only such resource.

Data-bearing resources must never be pruned or deleted by Argo CD. Removing them requires a separate manual, explicitly approved operation through Radar on cluster `kiTZ7VFRruo`, after backup/export and recovery review. A removed protected manifest leaves the Application out of sync; investigate it rather than overriding the protection. Keep the annotation in place. Application `syncPolicy.syncOptions` also includes `PruneLast=true`, delaying eligible stateless pruning until the final sync wave after other resources are healthy; this ordering does not replace data protection.

## Delivery responsibilities

Track 2 owns runtime, image, manifests, and CI. Track 3 owns database schema, migration contents, storage requirements, and jobs. Track 1 verifies the delivered UI. Requirements:

1. Build from the repository root using the pinned Node/pnpm versions and frozen workspace lockfile. Generate Prisma and build Next.js. Package the required runtime files and workspace dependencies in a non-root Linux image; verify the cluster CPU architecture. Never include `.env` or provider credentials.
2. Use one custom Node entry point for Next.js HTTP and authenticated WebSocket upgrades. Compile/package that entry point explicitly. Next.js [custom-server guidance](https://nextjs.org/docs/app/guides/custom-server) warns that standalone output does not trace custom server files. Preserve development HMR.
3. Add liveness/readiness probes, resource requests/limits, runtime Secret references, and graceful termination. Start with one replica. Handle overlap during rolling updates through durable host fencing, shared replay, and source-clock continuity.
4. Keep manifests under `infra` and workflows under `.github/workflows`. Adapt the starter's service and GitOps wiring to these paths. Build/test before publishing immutable image tags/digests; deploy the verified image. Use one delivery writer and prevent manifest-update loops or competing CI releases.
5. Use CloudNativePG with persistent storage for Postgres; verify provisioning and recovery.
6. Run versioned Prisma migrations once per release using a serialized Job before rollout; `db-migrate` implements this. Do not migrate from every pod startup. Prefer additive changes compatible with the previous image; rollback cannot undo destructive schema changes. Remove a required column over three releases: make it nullable while still writing it, then stop writing it, then drop it once no older image is a rollback target. An older Prisma client fails to read NULL from a field it declares required. `sessions.hostPrincipalId` is in the first phase. Verify backup/restore before real captured data.
7. Recaps run, and source cleanup will run, as [pg-boss jobs inside the app process](decisions.md#confirmed-by-the-track-3-owner); there is no worker Deployment or CronJob. The `db-migrate` Job creates and upgrades the `pgboss` schema. Each pod adds a pg-boss pool of at most three connections to Prisma's; review total database connections and app resource use.
8. Inject Dash0 OTLP and external service credentials at runtime. Scope Elastic keys and separate telemetry from capture content. Verify network access to each provider. No captured media belongs on ephemeral app disk.

[Next.js self-hosting guidance](https://nextjs.org/docs/app/guides/self-hosting) covers proxying, runtime environment variables, streaming, and cache behavior. ## S3 caption configuration (server only)

Production caption routes use Track 3's real membership authority whenever `DATABASE_URL` is configured; `SESSION_SECRET` verifies the principal cookie. `CAPTIONS_DEV_SESSION` never enables access with `NODE_ENV=production`.

| Variable               | Runtime source                                                                          | Behavior                                                                                                                                                                                             |
| ---------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `OPENAI_API_KEY`       | Optional Deployment Secret reference `app-credentials` / `OPENAI_API_KEY`; runtime only | Optional at boot; missing key reports degraded state (`missing_provider_key`). Never use build args or `NEXT_PUBLIC_`. No secret is created by S3.                                                   |
| `CAPTION_MODEL`        | Deployment plain environment value, not a Secret                                        | Defaults to `gpt-realtime-whisper`; server-side model ID.                                                                                                                                            |
| `CAPTION_DELAY`        | Deployment plain environment value                                                      | Defaults to `low`; accepts `minimal`, `low`, `medium`, `high`, `xhigh`.                                                                                                                              |
| `CAPTIONS_DEV_SESSION` | Explicit local environment; absent from checked-in cluster manifests                    | Enables one dev session outside production; 1–200 letters, digits, `.`, `_`, `-`; invalid IDs fail boot; not authentication. Ignored when `DATABASE_URL` is configured; otherwise unset rejects all. |

The Deployment wires the optional provider Secret reference and non-secret model/delay defaults. `optional: true` lets the pod start without the Secret/key; captions report missing-provider degradation for authorized members. With database configuration, the real authority enables the provider path in production when a key is supplied. Missing/invalid membership or access-backend failures still deny caption access. The cluster manifests do **not** set `CAPTIONS_DEV_SESSION`.

For an explicitly approved team demo, an operator must review a separate, temporary overlay setting `CAPTIONS_DEV_SESSION` to a valid session ID **and** `NODE_ENV=development` (the packaged server can run the built Next app in this mode). With `DATABASE_URL` absent, this bypasses membership for that single session and must be an explicit access decision, with isolated demo exposure and removal afterward. Setting the session flag alone in production does not enable access. No such overlay is checked in. A provider key would need separate operator provisioning; transport-only demos work without one and show degraded captions.

`CAPTION_RECONNECT_GRACE_MS` is optional server-only configuration: default 10,000 ms, integer 0–60,000. A normal host close (1000) means end of input; abnormal disconnects wait for same-epoch reconnect before finishing. Finishing has a five-second provider/sink budget, then emits a gap and fences late finals. SIGTERM keeps caption SSE open through that finish budget within the existing ten-second process drain and twenty-second pod grace (including the five-second preStop).

Validate manifests without reading a cluster configuration:

```sh
KUBECONFIG=/dev/null kubectl kustomize infra/k8s
```

This only renders local files; no cluster action is authorized by rendering. Do not configure provider access merely to run tests: `pnpm test` uses `ai/test` only. Keys, audio, transcripts, prompts, and raw provider errors must never enter logs. Sink failure is visible degradation plus a gap, not final publication. The process-local sink, replay log, audio receipt positions, and lease stub cannot provide restart/cross-pod durability.

### C2 runtime sink configuration

Supply both server-only `ELASTICSEARCH_URL` and `ELASTICSEARCH_API_KEY` in `app-credentials`, namespace `team-simon-says`, and inject both into the application environment. The Deployment references both keys. With neither or only one configured, the app boots and development captions visibly report `missing_elasticsearch_config` while using process-local storage. Malformed supplied values fail boot validation without echoing credentials.

The cloud indices were set up with `ELASTICSEARCH_INFERENCE_ID=.jina-embeddings-v5-text-small`; runtime uses the scoped app key and exact write aliases from the operator steps. No inference override is supplied by the runtime sink. The local integration uses `.multilingual-e5-small-elasticsearch` only; never copy that local override into cloud configuration without approval.
